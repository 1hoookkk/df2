# Independent UX judgment

**INFERRED — verdict:** DF2 Forge should not become a cube editor, a quarry map, a DSP laboratory, or a Blender-like general workspace. The strongest visible UX is a **chaptered listening bench** for one expert: find charged material, build the main morph, define the second movement, prove the exact playable surface, then keep or kill the body. The dominant screen subject should be the **audible body-in-progress**, not the generator that found it.

---

# 1. TEARDOWN — how a correct hidden architecture can still become an over-abstracted UI

**INFERRED:** The biggest UX risk here is not that the author sees too little technical truth. The risk is that the author sees the *wrong* truth: hidden generation spaces, false maps, fake axes, static-corner collections, or beautiful diagnostics that feel authoritative but do not answer the musical question.

A UI can become over-abstracted in this project through these failure modes:

## 1. Proposal-space leakage

The quarry, hidden descriptors, candidate generators, AI suggestions, and mathematical diagnostics are useful below the surface. But if the UI makes those structures feel like the thing being authored, the author starts operating the machinery instead of judging the sound.

**Relevant failure:** a large map of static candidates can make “find an interesting dot” feel like the job, when the actual job is “make one playable body that survives movement.”

## 2. Corner worship

A UI centered on “corners” encourages the author to fill locations and admire endpoints. That is seductive because static states are easy to see and compare. But the distinctive commercial result depends on the behavior between them.

**Relevant failure:** the old cube/corner language risks making the author believe that eight impressive static cards equal a strong preset.

## 3. False spatial authority

A 2D map, graph, cube, constellation, or physical-object metaphor can imply that screen distance equals musical distance. That may be false even if the hidden math is useful.

**Relevant failure:** low/high and closed/open may be a good retrieval surface, but it cannot safely imply trajectory compatibility, morph quality, drive behavior, or identity preservation.

## 4. Hidden-axis contamination

When the visible UI has more axes than the listener will perform, the author begins approving a hidden object. That is especially dangerous for a private authoring tool because it can feel powerful while creating results the public controls cannot honestly express.

**Relevant failure:** a visible cube implies a third authored dimension even if the consumer surface only has two continuous controls.

## 5. Diagnostic substitution

Response curves, stability warnings, novelty scores, pole/zero facts, and headroom lamps are useful. They are not taste. If they are visually dominant, the author can end up approving what looks valid rather than what sounds iconic.

**Relevant failure:** “middle stability” can be a helpful warning, but it must not become “middle is good.”

## 6. Plain-language drift

Plain language is good when it describes listening decisions. It is bad when poetic categories become fake physics.

“Throat,” “Vowel,” “Howl,” “Scream,” “Steel,” “Tube,” “Glass,” and “Mouth” can help memory. But if the UI treats them as formal filter classes, it will narrow the search and risk derivative thinking.

## 7. Video bias

Because this Forge is recordable, the UI must look confident. But a spectacular visual can make weak sound feel stronger during creation. The screen should make the author’s listening act legible, not theatricalize unapproved material.

**Relevant failure:** glowing curves and rainbow maps can look like achievement before the body has earned it.

## 8. Workflow ceremony

A sequential interface can be excellent. But if each section is merely a ritual panel, it slows the expert down. Every section must answer one audible question.

**Relevant failure:** “Shape / Player / Push” is close to a useful structure, but “Player” as a section is wrong if audition is needed everywhere.

## 9. AI-authority blur

AI suggestions must never visually look like human approval. If the UI inserts stations, repairs cells, or labels bodies with too much confidence, the author’s role becomes review of machine decisions instead of taste authority.

## 10. Over-building as rescue

Extreme filters will often fail in the middle. The UI must make killing weak bodies acceptable. If the surface editor makes it too easy to keep adding knots, lanes, labels, and repairs, the author will produce overfit bodies rather than iconic ones.

**OBSERVED:**

- **The graph topology is unclear.** The connecting lines imply a hidden structure, but the screen does not explain what the structure means musically.

- **No visible public control surface.** The author cannot see the actual MORPH × SECONDARY object being approved.

- **No approval state.** Nothing tells the author what is auditioned, locked, failed, or merely suggested.

### What is ambiguous

- Is the large green curve the currently selected corner, an interpolated middle, or a live position?
- Do the connecting lines represent interpolation, similarity, cube edges, or just layout?
- Are labels like “Vowel” fixed family names, candidate nicknames, or assigned roles?

### Preserve

- Large live response as a visual anchor.
- Mini candidate cards with plain-language labels.
- A confident dark aesthetic.
- Direct click-to-hear behavior.

### Discard

- The graph/cube topology as an authoritative body model.
- “Corner” as the main action word.
- Any implied hidden 3D structure.
- Free-floating labels without a clear listening question.

# 3. ONE-SENTENCE UX PRINCIPLE

**INFERRED — governing rule:**  
Every visible feature must help the author hear, choose, or prove the exact playable body; anything that describes a hidden generator, diagnostic, taxonomy, or proposal space must stay visually subordinate.

# 4. WORKFLOW VERDICT — Blender-like sequence or something else?

**INFERRED — verdict:**  
Use a **linear chaptered workflow**, but do **not** make it a Blender-like general workspace. The useful part of Blender is purposeful sections and visible state, not its density, 3D metaphor, mode complexity, or tool-panel sprawl.

The old “Shape / Player / Push” idea is close, but not correct. “Player” should not be a section because listening happens everywhere. “Shape” is too broad. “Push” may be confused with drive unless carefully framed.

The minimum useful visible chapters should be:

## 1. FIND

**Plain-language question:**  
“Is there a sound here worth building from?”

**Purpose:**  
Browse original static material quickly without pretending the browse map is the preset.

**Visible subject:**  
Candidate trays, small lossy map, mini response cards, clean-room badge, audition controls.

---

## 2. MORPH

**Plain-language question:**  
“Does the main movement stay alive from home to away?”

**Purpose:**  
Build the primary transformation before adding any secondary behavior.

**Visible subject:**  
A horizontal morph rail with locked stations, a ghost middle, sweep audition, and candidate replacements.

---

## 3. BEND

**Plain-language question:**  
“What does the second control add without becoming another preset?”

**Purpose:**  
Define the second movement as one coherent musical verb.

**Visible subject:**  
A sentence such as “BEND adds ___,” a high rail above the morph rail, vertical sweeps, and candidate deviations.

I would not call this “Secondary” in the main UI unless the author explicitly prefers product-coordinate language. “Bend” is plain, physical, and musical. The exact product coordinate can appear as smaller metadata.

---

## 4. PROVE

**Plain-language question:**  
“Does the playable surface survive the middle, sweeps, diagonals, clean, and driven?”

**Purpose:**  
Make approval about the actual body, not the stations.

**Visible subject:**  
The flat MORPH × BEND surface, cell status, proof deck, clean/driven audition, blind comparison.

---

## 5. KEEP

**Plain-language question:**  
“Is this one of the few bodies worth keeping?”

**Purpose:**  
Force a final taste decision and prevent overbuilt drafts from accumulating.

**Visible subject:**  
Body summary, signature gestures, provenance badge, proof status, set roster, keep/reject/park decisions.

---

## Why this is better than a full Blender-like model

- One expert does not need a general-purpose editor.
- The author is not building many presets; they are hunting a few exceptional bodies.
- Each chapter answers a musical question.
- The app can still feel mature and purposeful without exposing every hidden layer.
- The workflow remains recordable because the audience can understand what decision is being made.

# 5. EXACT PRESET-BUILDING SEQUENCE

This is one concrete authoring session from opening the app to keeping or rejecting one body.

---

## Step 1 — Open the app

**Author sees:**  
A body shelf with empty or draft slots, a clean-room badge, a persistent audition strip, and a large button: “New Body.”

The top chapter strip reads:

**FIND / MORPH / BEND / PROVE / KEEP**

No cube. No atlas-first spectacle. No raw coefficients.

**Author does:**  
Creates a new body and optionally writes a short private brief, for example:

> “crooked throat that tears open into bright metal”

**Author hears:**  
The dry audition loop or selected probe source, not yet processed.

**Why this exists:**  
The session starts with intent, not technology.

---

## Step 2 — Enter FIND

**Author sees:**  
A compact candidate area, not a huge dot field. The visible retrieval surface has:

- five material drawers: Weight, Mouth, Teeth, Wire, Air;
- a small low/high and closed/open browse map;
- candidate cards with mini response traces;
- tags such as hollow, sharp, heavy, torn, nasal, open, unstable-feeling;
- a clean-room/provenance indicator.

The map is labeled clearly as a **browse projection**, not truth.

**Author does:**  
Clicks candidates from a tray such as:

- Charged
- Sparse
- Violent
- Similar to starred
- Far contrast

**Author hears:**  
Each candidate instantly through the selected audition source, with quick clean/driven toggles.

**Why this exists:**  
The author needs emotional raw material quickly, not a lesson in the generator.

---

## Step 3 — Pin a HOME state

**Author sees:**  
One candidate enlarged as a station card labeled HOME. It appears at the left side of a simple morph rail. The large live response trace updates.

**Author does:**  
Pins the candidate or rejects it.

**Author hears:**  
A held preview and a short loop through the candidate, clean and optionally driven.

**Why this exists:**  
The body needs a recognizable starting identity.

---

## Step 4 — Choose an AWAY contrast

**Author sees:**  
A contrast tray appears: “Try these as the far end.” The morph rail now has HOME on the left and ghost candidates on the right.

**Author does:**  
Clicks possible AWAY candidates and drags a large MORPH control from 0 to 1.

**Author hears:**  
A direct sweep from HOME to AWAY, first clean, then driven.

**Why this exists:**  
The primary story must be strong before the UI introduces any second dimension.

---

## Step 5 — Check the middle immediately

**Author sees:**  
A ghost card appears at the midpoint of the morph rail:

> MIDDLE — unheard

The UI offers simple actions:

- Play middle hold
- Play slow sweep
- Play fast gesture
- Mark strong
- Mark weak

**Author does:**  
Auditions the direct middle and the sweep.

**Author hears:**  
Whether the sound keeps its identity, loses level, collapses, becomes mush, or becomes unexpectedly great.

**Why this exists:**  
This catches the central failure early. It also prevents the author from falling in love with endpoints that do not move.

---

## Step 6 — Repair or lock the morph rail

**Author sees:**  
If the middle fails, only the weak segment is highlighted. A bridge tray appears with candidates labeled as suggestions, not solutions.

If the middle works, the UI makes that visible and does not pressure the author to add another station.

**Author does:**  
Either:

- locks HOME and AWAY;
- replaces one endpoint;
- inserts one bridge station;
- or kills the rail.

**Author hears:**  
Local segment sweeps around only the changed region.

**Why this exists:**  
The rail stays sparse. The author repairs audible failure, not visual emptiness.

---

## Step 7 — Define BEND

**Author sees:**  
A sentence prompt:

> When BEND rises, this body becomes ______.

The UI may offer plain suggestions, but the author can write their own:

- more hollow
- sharper
- more pressurized
- more airless
- more torn
- more nasal
- heavier
- more open

**Author does:**  
Selects or writes one intended second movement.

**Author hears:**  
A few candidate deviations at the HOME station.

**Why this exists:**  
The second control must be a coherent performance verb, not another hidden preset selector.

---

## Step 8 — Build the high-BEND rail

**Author sees:**  
A second rail appears above the base morph rail. The screen now shows a simple two-rail surface:

- lower rail: base BEND
- upper rail: high BEND

Each morph station has a corresponding high-BEND target slot.

**Author does:**  
For each locked morph station, chooses a high-BEND version from candidates.

**Author hears:**  

- vertical sweep at HOME;
- vertical sweep at any bridge station;
- vertical sweep at AWAY;
- morph sweep along the high-BEND rail.

**Why this exists:**  
The author verifies that BEND changes the body without breaking its identity.

---

## Step 9 — Enter PROVE

**Author sees:**  
The actual flat playable surface becomes the main subject. It is not a cube. It is a simple plate with:

- MORPH horizontally;
- BEND vertically;
- stations as locked points;
- cells as regions requiring proof;
- a moving puck showing the current control position;
- cell statuses: unheard, rendered, failed, approved.

A proof deck appears beside or below the surface.

**Author does:**  
Selects a cell and plays the proof deck.

**Author hears, at minimum:**  

- center hold;
- MORPH sweep along the lower side;
- MORPH sweep along the upper side;
- BEND sweep at the left side;
- BEND sweep at the right side;
- diagonal one way;
- diagonal the other way;
- clean version;
- driven version.

**Why this exists:**  
The author approves the thing the listener will actually play.

---

## Step 10 — Repair only what failed

**Author sees:**  
If a cell fails, the UI marks the exact failed test:

- center failed;
- upper morph sweep failed;
- vertical sweep failed;
- diagonal failed;
- driven version failed.

Suggestions appear in context:

- replace this station;
- try this bridge;
- insert a local morph station;
- add a middle BEND lane;
- kill body.

**Author does:**  
Chooses the smallest audible repair or rejects the body.

**Author hears:**  
Before/after comparisons on the failed gesture only.

**Why this exists:**  
Extreme sounds will fail often. The UI must make minimal repair faster than overbuilding.

---

## Step 11 — Blind comparison

**Author sees:**  
The surface view temporarily disappears. The screen shows anonymous render cards:

- A
- B
- C

The author does not see station count, representation, AI notes, or suggested winner.

**Author does:**  
Scores the renders for keep desire, middle integrity, boldness, BEND clarity, drive behavior, and playability.

**Author hears:**  
Matched renders of the current body and simpler alternatives where useful.

**Why this exists:**  
It prevents the author from preferring the version that looks more sophisticated.

---

## Step 12 — KEEP or reject

**Author sees:**  
A body card with:

- private body name or working title;
- brief;
- signature gestures;
- clean-room badge;
- stations locked;
- cells approved;
- failed tests resolved or acknowledged;
- body complexity summary;
- Keep / Park / Reject.

**Author does:**  
Keeps, parks, or rejects the body.

**Author hears:**  
Three short signature gestures: low BEND, high BEND, and diagonal performance.

**Why this exists:**  
The final decision is human taste. The UI supports confidence, but it does not approve for the author.

---

## Step 13 — Return to the set wall

**Author sees:**  
A roster of the current body set, aiming toward a small final group. Each kept body has a signature gesture and a few plain descriptors. Overlap warnings are visible but subdued.

**Author does:**  
Compares the new body against the set and either gives it a slot, parks it, or deletes it.

**Author hears:**  
A/B snippets across kept bodies.

**Why this exists:**  
A body can be good alone and redundant in the final set.

# 6. TAXONOMY VERDICT

## Is low/high × closed/open the strongest simple retrieval model?

**INFERRED — verdict:**  
No, not by itself. A visible low/high and closed/open picker is useful as a **browse floor**, but it is too weak to be the main retrieval model for extreme morphing filters.

It can help answer:

- Is the action mostly low, mid, or high?
- Is the state broadly obstructed or open?
- Is this candidate roughly in the zone I want?

It cannot reliably answer:

- Is this vocal, comb-like, hollow, sharp, phase-smeared, or unstable-feeling?
- Will this morph well with another state?
- Will it survive drive?
- Is this static state part of a coherent body?
- Is this candidate genuinely novel or just visually separated?
- Does the middle collapse?

So the best visible retrieval model is:

> **material drawers + compact candidate trays + a small low/high closed/open browse projection.**

The taxonomy retrieves; the map orients.

---

## If used, define the 2D map precisely

**Low ↔ High**  
This is not pitch. It means where the dominant audible filter action lives:

- low resonance and weight;
- mid body/cavity;
- upper bite, air, scream, or needle behavior.

**Closed ↔ Open**  
This is not quality. It means how much the filter feels obstructed versus exposed:

- closed: narrowed, muted, blocked, swallowed, notched, dark;
- open: broadband, exposed, airy, bright, released.

**Important UI language:**  
The map must be labeled:

> Browse projection — not morph distance.

Do not rank-spread dots to fill the screen. Do not let the author believe empty map space equals missing sonic possibility.

---

## Smallest useful mental taxonomy

**INFERRED:** The smallest useful taxonomy should be a set of **material drawers**, not mathematical classes.

I recommend five visible drawers:

## 1. Weight

**Feels like:** body, mass, chest, floor, pressure, low growl.  
**Useful for:** heavy lows, broad dark bodies, sub-resonant pressure, physical weight.  
**Visual identity:** thick slabs, low silhouettes, slow heavy motion.

## 2. Mouth

**Feels like:** throat, vowel, nasal, cavity, formant motion, body tube.  
**Useful for:** vocal-tract motion, talking filters, hollow vowels, impossible throats.  
**Visual identity:** rounded cavities, tube cross-sections, resonant pockets.

## 3. Teeth

**Feels like:** bite, scream, sharpness, needle, tearing edge.  
**Useful for:** unstable resonant edges, high-impact peaks, violent upper motion.  
**Visual identity:** angular cuts, sharp triangular highlights, hot rims.

## 4. Wire

**Feels like:** comb, metallic, notch ladder, string, phase smear, inharmonic structure.  
**Useful for:** impossible physical objects, ringing lattices, torn interference, non-vocal weirdness.  
**Visual identity:** thin lines, parallel notches, vibrating filaments.

## 5. Air

**Feels like:** open, breath, haze, exposed top, hollow space, diffuse release.  
**Useful for:** opened states, high-air transformations, spectral release, light endings.  
**Visual identity:** soft halos, open arcs, misty fields.

## Overlay: Danger

This is not a drawer. It is a risk/intensity layer.

**Feels like:** calm, hot, redline, unstable-feeling, drive-danger.  
**Useful for:** preserving extreme material without making “violence” a genre.  
**Visual identity:** rim heat, warning ticks, ember outline, not a full red flood.

---

## Does this cover the intended sonic spectrum?

Mostly, yes.

| Desired region | Covered by |
|---|---|
| vocal-tract motion | Mouth |
| throat/vowel/nasal behavior | Mouth + Weight |
| low growl / body | Weight |
| unstable resonant edges | Teeth + Danger |
| scream / howl / bright bite | Teeth |
| impossible physical objects | Wire + Mouth or Wire + Air |
| comb-like/notched/ripped behavior | Wire |
| open-air or exposed top | Air |
| heavy-to-open transformations | Weight → Air |
| violent transformations | any drawer + Danger |
| smooth conventional filter shapes | Weight / Air, but intentionally not over-celebrated |

## Missing or weak regions

**INFERRED:**

- **Drive-dependent identity** is not covered by taxonomy. It must be auditioned.
- **Trajectory compatibility** is not covered. It must be proved in MORPH and PROVE.
- **Phase-heavy weirdness** may be under-recognized visually. It should appear as Wire/Air tags such as smear, drag, or ghost.
- **Very smooth ordinary filtering** may feel underrepresented. That is acceptable if the product ambition is extreme and distinctive, but the drawer system should still allow calm candidates.
- **Level/headroom behavior** should not become a family. It is a warning layer.

---

## How visual identities should attach

**INFERRED:** Use the taxonomy as memory and retrieval, not truth.

- Candidates may belong to multiple drawers.
- A candidate can be Mouth + Wire + Danger.
- Drawer identity should appear as a small chip, icon, card edge, or texture.
- Do not give each drawer a giant saturated background.
- Do not make the author choose “the Mouth algorithm.”
- Do not name final commercial presets directly after drawers unless the author later decides that is artistically right.

# 7. CONTEXTUAL DEPTH — what deeper operations should look like

The Forge should show depth only when it answers the current audible question.

---

## Midpoint checks

**INFERRED:** Midpoint checks should be visible and first-class, but not technical.

Show them as ghost checkpoints on the rail or cell:

- Middle unheard
- Middle played
- Middle strong
- Middle weak
- Middle replaced

The author should get one obvious action:

> Play middle

Diagnostics can appear only if there is a problem:

- level drop
- headroom risk
- render failed
- drive danger

Do not show raw interpolation math.

---

## Secondary behavior

**INFERRED:** The second movement should appear only after the base morph has a reason to exist.

The visible prompt should be:

> When BEND rises, this body becomes ______.

Then the UI shows vertical sweeps and the high rail.

Avoid early grids. Avoid exposing “secondary” as a blank axis to fill. The author must first decide what it means musically.

---

## Audition comparisons

**INFERRED:** Audition comparison should be persistent and fast.

The UI should always offer:

- clean preview;
- driven preview;
- current gesture;
- replay last;
- A/B before/after;
- blind compare when judging final alternatives.

Comparisons should be heard before they are explained.

The proof deck should be practical, not elaborate:

- center;
- horizontal sweeps;
- vertical sweeps;
- diagonals;
- performance gesture;
- clean/driven.

---

## Body approval

**INFERRED:** Approval should be explicit and human-stamped.

Visible statuses:

- unheard;
- auditioned;
- locked;
- failed;
- repaired;
- approved;
- kept;
- rejected.

Do not use:

- AI approved;
- auto approved;
- likely good;
- model confidence;
- publishable score.

If AI proposes a candidate, it should be visually marked as a suggestion until the human locks it.

---

## Diagnostics

**INFERRED:** Diagnostics should be visible as warning lamps and expandable detail, not permanent visual noise.

Useful visible warnings:

- driven risk;
- level drift;
- duplicate risk;
- failed render;
- headroom danger;
- unapproved cell;
- middle failed;
- diagonal failed;
- provenance issue.

Do not make pole/zero diagrams, coefficient tables, or hidden descriptor plots part of the taste surface.

---

## Provenance

**INFERRED:** Provenance should appear as a trust badge by default, with detail on demand.

Default:

> Clean-room generated

Detail popover:

- internal seed/parent IDs;
- algorithm version;
- no external coefficients;
- no imported presets;
- no copied names.

Do not display categories that imply third-party lineage.

---

# 8. VISUAL LANGUAGE

## Direction

**SPECULATIVE but recommended:**  
Use a **dark cinematic materials-bench aesthetic**: quiet, high-contrast, technical enough to feel mature, but with one luminous sonic object at the center.

The UI should feel like:

- a private instrument lab;
- a destructive filter forge;
- a recording-ready decision surface;
- not a consumer preset browser;
- not a game UI;
- not a DAW clone;
- not a fake 3D physical simulator.

---

## Dominant visual subject

**INFERRED:**  
The dominant visual subject should be the **body-in-progress**:

- in FIND: candidate cards plus one large live response;
- in MORPH: the morph rail and live response;
- in BEND: the two-rail surface beginning to form;
- in PROVE: the actual flat playable surface;
- in KEEP: the final body card and signature gestures.

The large glowing response curve from the old Forge is worth preserving, but it must become an auditory sketch attached to decisions, not the only truth.

---

## Hierarchy

1. **Current musical question**  
   Large and plain: “Does the middle survive?” / “What does BEND add?”

2. **Current audible object**  
   Rail, surface, station card, or live response.

3. **Immediate actions**  
   Play, lock, fail, replace, keep, kill.

4. **Candidate suggestions**  
   Tray cards, not giant maps.

5. **Status and provenance**  
   Always visible, visually quieter.

6. **Diagnostics**  
   Only loud when something fails.

---

## Graph treatment

Use graphs as **audition artifacts**, not abstract territories.

Recommended graph forms:

- large live response ribbon;
- mini response fingerprint cards;
- flat MORPH × BEND surface;
- rail with station cards;
- proof deck with rendered gesture cards.

Avoid:

- 3D cubes;
- opened cubes;
- graph spaghetti;
- perspective surfaces;
- giant constellation maps as the main workspace;
- decorative connecting lines that do not correspond to playable movement.

If a quarry projection is shown, label it clearly:

> Browse projection

or

> Retrieval view — not morph distance

---

## Color strategy

## Evaluate 60:30:10

**INFERRED:**  
A 60:30:10 strategy is useful only as **area discipline**, not as a complete semantic color system.

Strict 60:30:10 fails here because the Forge needs multiple small semantic colors:

- family tags;
- warning states;
- clean/driven;
- locked/failed statuses;
- live signal.

But 60:30:10 is useful to prevent the old UI’s rainbow-map overload.

## Recommended color allocation

### 60% — dark canvas

Use deep, nearly black surfaces:

- Void: `#050809`
- Panel black: `#0B1115`
- Raised panel: `#10191E`

Function:

- cinematic base;
- reduces visual fatigue;
- makes the live sound object dominant;
- good for screen recording.

### 30% — structural blue-green graphite

Use desaturated grid, borders, and secondary text:

- Grid: `#14262C`
- Panel stroke: `#1C3A42`
- Muted teal: `#315E66`
- Secondary text: `#7F9697`
- Main text: `#E3ECE6`

Function:

- mature audio-tool clarity;
- technical scaffolding;
- avoids pure neon chaos.

### 10% — live signal and decision accent

Use one main luminous signal color:

- Ion green: `#7CFF5B`

Function:

- current live response;
- current puck;
- locked human approval;
- “this is the sound right now.”

### Semantic micro-colors

These should be small accents only: card rims, chips, icons, not full-screen fills.

- Weight: burnt amber `#C9852B`
- Mouth: yellow-green `#A7E85A`
- Teeth: hot red `#FF4A4A`
- Wire: violet `#A873FF`
- Air: cyan `#49D8FF`
- Warning/drive risk: ember `#FF7A2F`
- Hard fail: red `#FF2F4F`

Function:

- memory;
- scanability;
- not decorative dominance.

---

## Typography character

**SPECULATIVE but recommended:**

Use three typographic voices:

1. **Chapter/question type**  
   Condensed, uppercase, confident. Industrial but not sci-fi parody.

2. **Readable instruction type**  
   Human, plain sans. Used for verbs: Play, Lock, Replace, Kill, Keep.

3. **Status/ID type**  
   Monospace or tabular numerals for station IDs, counts, render statuses, provenance IDs.

Avoid cryptic main labels such as:

- M100/Q0;
- Z1 ceiling;
- C08;
- XFORM;

unless they are secondary metadata.

---

## Motion

Motion should be tied to audition.

Use:

- puck moving along MORPH/BEND during playback;
- response trace blooming while sound plays;
- proof deck progress during sweeps;
- subtle lock stamp when human approves;
- warning pulse only when action is needed.

Avoid:

- decorative background animation;
- fake fluid simulations;
- spinning 3D objects;
- animated maps that imply false intelligence;
- constant glow that makes everything feel equally important.

---

## Recordable mode

**INFERRED:**  
Because short-form content is part of the private workflow, include a recordable framing mode.

Recordable mode should:

- keep the current chapter and musical question visible;
- enlarge the live response and surface;
- hide deep diagnostics unless failing;
- show clean-room badge;
- show human decisions: locked, failed, kept;
- keep candidate names plain and original;
- never expose prohibited references or raw technical dumps.

It should not be a separate “marketing skin.” It should be the same truthful UI with better framing.

# 9. OPPORTUNITY AUDIT

These are the most important overlooked opportunities.

---

## 1. Make the current musical question unavoidable

Every chapter should display one question in large text.

Examples:

- “Is this seed worth building from?”
- “Does the middle survive?”
- “What does BEND add?”
- “Does this cell pass driven?”
- “Is this one of the few?”

**Why it matters:**  
It prevents the author from drifting into map browsing, corner filling, or diagnostic tweaking.

---

## 2. Add a gesture recorder inside authoring

**INFERRED:**  
The author should be able to record a short MORPH/BEND movement as a gesture and replay it through candidate bodies.

**Why it matters:**  
Extreme morphing filters are performance objects. Static sweeps are necessary but not sufficient. This also directly supports short-form recording.

---

## 3. Make killing a body easy and respectable

The UI should have a strong “Kill Body” or “Reject Body” action with optional reason tags:

- weak middle;
- BEND confused;
- too timid;
- too derivative;
- driven failed;
- overbuilt;
- not iconic.

**Why it matters:**  
The goal is 4–7 exceptional bodies, not saving every draft.

---

## 4. Use blind simplification before final keep

The author should hear simpler versions without seeing which is simpler.

**Why it matters:**  
A complex surface can look more intentional even when it sounds no better.

---

## 5. Treat “same but more” as a retrieval operation

When building BEND, candidate retrieval should not show generic map neighbors. It should show:

> same body, more hollow  
> same body, sharper  
> same body, more airless  
> same body, more torn

**Why it matters:**  
This helps keep BEND from becoming a hidden preset selector.

---

## 6. Use a set wall early

Even while authoring one body, keep a small roster of kept/parked bodies visible somewhere quiet.

**Why it matters:**  
Commercial distinctiveness is relative. A body can be excellent and still redundant.

---

## 7. Use provenance as visible confidence, not paperwork

A small clean-room badge should appear in recordable mode and final keep views.

**Why it matters:**  
The project’s originality constraint is part of the product story, but the author should not browse legal metadata all day.

---

## 8. Do not let physical metaphors become fake simulation

Physical bodies, materials, and objects are useful as memory skins. They are dangerous as literal UI models.

**Challenge to assumption:**  
A beautiful “impossible object” editor could be worse than a plain rail if it hides the actual MORPH/BEND behavior.

---

## 9. Preserve ugly candidates longer than the UI wants to

The visual system will naturally make ugly, violent, or sparse states look like errors. The Forge should keep a violent/outlier tray with clear safety warnings.

**Why it matters:**  
Commercially distinctive extreme presets often come from material that looks wrong at first.

---

## 10. Make clean/driven mismatch a visible authoring event

If a body passes clean and fails driven, that should be a major visible story, not a warning buried in a diagnostics drawer.

**Why it matters:**  
The drive path is part of perceived character. A private Forge that hides this will create false positives.

---

## H. Navigation model

Use simple linear navigation with backtracking:

- FIND can return to Body Shelf.
- MORPH can return to FIND.
- BEND can return to MORPH.
- PROVE can return to BEND or MORPH for repair.
- KEEP can return to PROVE or place the body in the set.

Use modal overlays only for:

- blind comparison;
- candidate detail;
- diagnostic detail;
- record framing.

No nested editor labyrinth. No hidden workspaces. No cube/atlas mode that becomes a second product.

---

# Firm recommendation

**Build DF2 Forge as a chaptered listening bench: FIND → MORPH → BEND → PROVE → KEEP.**  
Use the low/high and closed/open map only as a small lossy retrieval aid under a five-drawer material taxonomy. Make the actual flat playable body the visual authority. Preserve the old Forge’s best qualities — large live response, plain evocative labels, candidate cards, persistent audition controls, confident dark aesthetic — but discard the cube, the full-screen atlas-as-truth, hidden axes, raw DSP surfaces, and any UI that rewards corner collection over hearing the moving body.
